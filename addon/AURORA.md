# Edit your module in Aurora

Use a staging copy of your own module. These instructions are for the generic bridge import generated by `bash addon/setup.sh prepare`. The supplied YourWorld_Fixed investigation already has Role Weaver and story hooks: keep its `rq_load`, `rq_chat`, `rq_enter` and `rq_exit` events instead.

## 1. Make a working copy

Stop editing the same module in multiple places. Copy your Linux server's `.mod` to Windows, preserving its filename. Keep an untouched backup outside the active modules folder. Open the working copy in Aurora. Supply its required HAKs/TLK files too.

Transfer the generated **RoleWeaver-Import.erf** from Ubuntu to Windows. You do not need to transfer its entire builds folder.

## 2. Import the resources

In Aurora, choose **File → Import**, select **RoleWeaver-Import.erf**, and import its resources.

If Aurora asks to replace existing `rw_*` scripts or blueprints, stop and compare them with your current integration. If it asks to replace `nwnx_*` headers, verify they are the same version used by your server and other scripts. Do not overwrite an established world's customized headers without review.

The import places these resources INSIDE the module:

| Resources | Purpose |
| --- | --- |
| `rw_*.nss`, including generated `rw_settings` | Role Weaver bridge and your world ID/Redis prefix |
| `nwnx_core`, `nwnx_chat`, `nwnx_events`, `nwnx_redis`, `nwnx_creature`, `nwnx_player` and their required includes, such as `nwnx_redis_lib` | Compiler headers matching your installed NWNX build |
| `rw_base.utc` | Creature blueprint for dashboard spawning |
| `rw_shop.utm` | Store blueprint for merchants |
| `rw_userload`, `rw_userchat` | Small editable event scripts for a NEW module |

The generated manifest lists the exact included files and hashes. NWNX `.so` plugins belong on Linux, never inside the module. Include scripts have no `main()` and normally produce no `.ncs` of their own.

## 3. Connect the module events

Open **Edit → Module Properties → Events**. Write down the existing values for **OnModuleLoad** and **OnPlayerChat** before changing anything.

### If those two events are empty (a new module)

Set **OnModuleLoad** to `rw_userload` and **OnPlayerChat** to `rw_userchat` (no filename extension). Leave other events alone. Open either template in the Script Editor if you want to edit it; comments explain its purpose.

### If either event already has a script (an existing world)

Keep the existing event assignments. Open the existing load script, and add this line after normal initialization, inside its `main()` function:

```c
ExecuteScript("rw_init", GetModule());
```

For chat, place the following line INSIDE the existing handler's approved-message path, after its filtering checks:

```c
ExecuteScript("rw_modulechat", OBJECT_SELF);
```

Do not simply wrap an unknown chat script and forward every message afterward: early returns, private messages and moderation decisions must still be respected. If your world uses an NWNX Chat callback, use `rw_chat` from inside that callback instead. Install exactly one chat route. The [integration reference](INTEGRATION.md) covers custom frameworks; the world's script maintainer should choose the approved-message point.

## Optional DM spawning

To allow dashboard spawning, edit the two FALSE values in `rw_userload` to TRUE. For an existing load handler, add the same `SetLocalInt` calls from the template after `rw_init`. The two flags are:

- `rw_allow_dm_spawn`: lets a connected DM create NPCs at their location.
- `rw_allow_persistent_spawn`: lets Role Weaver save and restore those DM-created NPCs.

After installing the companion, open `~/.local/share/roleweaver/my_world/config.json` on Ubuntu (replace my_world if you changed it). Set `allow_dm_spawn` to `true`; set `allow_persistent_spawn` to `true` if you enabled it in the module. Preserve all other settings. Run `bash addon/setup.sh restart` from the package folder.

Keep these disabled if your world owns all spawning/persistence. Existing world NPCs can still be bound. Shops and other actions are enabled per NPC in the dashboard; they do not require another module event.

## 4. Compile and save

Use **Build → Build Module**, enable **Compile**, and build. Resolve compile errors before deployment. Warnings about unused scripts are expected for resources called by name, but missing resources or compile errors must be fixed.

If `nwnx_redis_lib` or another include is missing, check that the import used the matching full NWScript download. Do not delete the include or disable the script to silence the error. A `rw_*` compile error can also indicate an older copy in an override/HAK or a conflicting prior integration.

Save the module. Confirm that the saved `.mod` has a new modification time. Compiled entry scripts are saved inside this module along with their sources and the imported blueprints.

## 5. Put the saved module back on Linux

1. Arrange downtime and stop ONLY the NWN instance that loads this module, using its existing service/launcher. For the supplied foreground launcher, enter `quit` in its game console and wait for it to exit.
2. Back up its current `.mod` outside the active modules folder.
3. Copy the saved Windows `.mod` into that server's existing `modules` folder, replacing the intended filename. For the new-server example this is `~/nwn-world/modules/YourWorld.mod`.
4. Start that same server with the same module name (omit `.mod` in the launcher setting).
5. Confirm the module and NWNX plugins loaded, then follow Step 6 of START_HERE.md.

For this ERF workflow, do NOT also copy generated scripts to override. The resources are inside your saved module. Established worlds using a build pipeline can instead integrate scripts/ through that pipeline, with their normal resource-precedence rules.

The Python companion does not replace your module, import HAKs or start NWN. Player memories and NPC profiles live in the companion's data folder and survive module updates.
